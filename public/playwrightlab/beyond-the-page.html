Getting started

Everything else on this page assumes you can already write and run one Playwright test. If you can't yet, start here — then PlaywrightLab's hands-on locator practice, and the rest of this page, will actually make sense instead of being a wall of unfamiliar syntax.

Install & scaffold a project

npm init playwright@latest

This one command asks a few questions — TypeScript or JavaScript, where your test files should live (default: tests/), whether to add a GitHub Actions workflow, and whether to install browser binaries now — then generates a working project: a playwright.config.ts, an example test, and a tests-examples/ folder worth skimming once and deleting.

npx playwright install

Browser installation is a separate step on purpose: Playwright doesn't drive your system's Chrome or Firefox, it downloads its own known-good builds of Chromium, Firefox, and WebKit and drives those directly. That's also why a test can behave differently from what you see in your everyday browser — it's not always the same binary or the same version.

Anatomy of a test file

Almost every Playwright test follows the same three-part shape: go somewhere, do something, check something happened.

// tests/example.spec.ts
import { test, expect } from '@playwright/test';

test('homepage has the right title', async ({ page }) => {
  await page.goto('https://playwright.dev');
  await expect(page).toHaveTitle(/Playwright/);
});
  • test(name, fn) — one test case. The function receives an object you destructure fixtures out of — { page } here is Playwright handing you a fresh, isolated browser tab for this test only.
  • await — nearly every Playwright call is async, because each one is really a message sent to a real browser and a reply waited for. Forget an await and the test moves on before the action finished — usually surfacing as a confusing failure two lines later, not on the line actually missing it.
  • expect(...) — the assertion. Covered in full below, but notice it's also awaited — that's not a typo, it's the single most important thing to understand about how these assertions differ from a plain assert().

Running tests

# run everything, headless, and print a pass/fail summary
npx playwright test

# watch it happen in a real browser window instead of headless
npx playwright test --headed

# pause on failure and step through with the Playwright Inspector
npx playwright test --debug

# just one file, or just tests whose name matches
npx playwright test tests/example.spec.ts
npx playwright test --grep "homepage"

A run ends with a summary line (3 passed, 1 failed) and, on any failure, a command to open the full HTML report — that report is the same one below build on. --debug is worth reaching for before anything fancier: it opens the Playwright Inspector and pauses before every action, which is often enough to see exactly where an assumption about the page was wrong.

The assertion library, and why it's different

A plain assertion checks a value once, immediately, and is wrong by nature for a browser: the element you want almost certainly doesn't exist the instant your test starts, because the page is still loading, an animation hasn't settled, or data hasn't arrived from an API yet. Playwright's expect(locator) assertions are web-first — they retry automatically for a few seconds until the condition is true or a timeout is hit, which is the entire reason PlaywrightLab's dynamic-content and waits panels don't need any manual sleep() calls to pass reliably.

await expect(locator).toBeVisible();
await expect(locator).toHaveText('Submitted');
await expect(locator).toHaveValue('tester');
await expect(locator).toBeEnabled();
await expect(locator).toBeChecked();
await expect(locator).toHaveCount(3);
await expect(page).toHaveURL(/checkout/);
await expect(page).toHaveTitle('PlaywrightLab');
  • toBeVisible / toBeHidden — the two you'll write most often, since "did the right thing show up" is most of what a UI test checks.
  • toHaveText / toContainText — exact match vs. substring; reach for toContainText when only part of a string is stable (a dynamic timestamp appended to a fixed label, for example).
  • toHaveValue / toBeChecked — form state: an input's current value, or a checkbox/radio's checked state.
  • toHaveCount — asserts on how many elements a locator matches, useful for "the list has 3 rows" rather than inspecting each row.
  • toHaveURL / toHaveTitle — assert on the page itself rather than an element on it, typically after a navigation or form submission.

The missing await is the single most common beginner mistake here — without it, the assertion fires immediately, fails on a page that hasn't finished loading, and the error looks like a real bug in the app rather than a missing keyword in the test.

01

Test architecture

PlaywrightLab teaches you to find and act on one element at a time. It has no opinion on how a hundred tests should be organized so the suite stays readable a year from now. That's this page's job.

Page Object Model (POM)

Without it, a locator like page.getByTestId('auth-username') gets copy-pasted into every test file that touches login. The day someone renames that field, you're doing a find-and-replace across the suite instead of editing one file — and the tests that only run nightly won't tell you they're broken until they do.

Wrap a page's locators and actions in a class instead. Tests read like user stories ("log in, then assert the session") instead of a wall of selectors, and when a locator changes you fix it in one place. The class stays dumb on purpose — it exposes locators and low-level actions, not assertions — so a failing expect() still points at the test that broke, not at some helper three files away.

// pages/login-page.ts
export class LoginPage {
  readonly page: Page;
  readonly username: Locator;
  readonly password: Locator;
  readonly submit: Locator;

  constructor(page: Page) {
    this.page = page;
    this.username = page.getByTestId('auth-username');
    this.password = page.getByTestId('auth-password');
    this.submit = page.getByRole('button', { name: 'Log in' });
  }

  async loginAs(user: string, pass: string) {
    await this.username.fill(user);
    await this.password.fill(pass);
    await this.submit.click();
  }
}
// tests/login.spec.ts
test('rejects a wrong password', async ({ page }) => {
  const login = new LoginPage(page);
  await page.goto('/playwrightlab.html');
  await login.loginAs('tester', 'wrong');
  await expect(page.getByTestId('auth-error')).toBeVisible();
});

One page, one class is the common convention, but it's not a law — for a small suite, a handful of shared locator constants can be enough. Reach for full POM classes once the same flow (login, checkout, search) is driven from three or more spec files.

Custom fixtures

Every test that needs a logged-in user could just call await new LoginPage(page).loginAs(...) in its first line — but now that call is duplicated everywhere, and it runs freshly, serially, inside every single test even though the outcome never differs. A fixture does the same setup once per test in a shared, declarative way, and — critically — only actually runs for tests that ask for it, so tests that don't need auth don't pay for it.

Playwright's test.extend() lets you inject setup — like an already-logged-in page — instead of repeating it in every test's first three lines. Fixtures can depend on each other (a fixture can request another fixture the way a test does), so you can build up a chain — loggedInPage depends on page, an adminPage fixture could depend on loggedInPage — and Playwright resolves the order for you.

// fixtures.ts
import { test as base } from '@playwright/test';
import { LoginPage } from './pages/login-page';

export const test = base.extend<{ loggedInPage: Page }>({
  loggedInPage: async ({ page }, use) => {
    await page.goto('/playwrightlab.html');
    await new LoginPage(page).loginAs('tester', 'playwright');
    await use(page); // hand the ready-to-go page to the test
  },
});
test('logged-in users see their session', async ({ loggedInPage }) => {
  await expect(loggedInPage.getByTestId('auth-whoami')).toHaveText('tester');
});

Organizing with test.describe

A flat folder of 200 test() calls works fine on day one. It stops working the day CI takes 40 minutes and someone asks "can we just run the checkout tests" — and the honest answer is "not without grep-ing filenames." These four habits are what keep a suite navigable as it grows, roughly in the order you'll feel the pain:

  • Group by feature, not by page — describe('checkout') beats describe('CartPage') once a single flow spans multiple pages, which most real flows do.
  • test.beforeEach inside a describe block for setup shared by that group only — it won't silently run for tests in a sibling describe block that don't need it.
  • test.step('fill shipping form', async () => {...}) to make trace-viewer timelines and failure output readable at a glance — without steps, a failure just says "line 47," and you're left reading the whole test to figure out which logical phase it was in.
  • Tag with test('...', { tag: '@smoke' }, ...) and filter with --grep @smoke in CI — this is what lets a PR pipeline run a 2-minute smoke subset instead of the full 40-minute suite, saving the full run for a nightly job.
02

playwright.config.js

One file controls which browsers you run against, how flaky failures are retried, and what evidence gets kept when something breaks. PlaywrightLab only ever runs in whatever browser you happened to open it in.

Cross-browser and device projects

// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 2 : undefined,
  reporter: 'html',
  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
    { name: 'mobile-chrome', use: { ...devices['Pixel 7'] } },
  ],
});

What each setting is actually for

None of these are defaults to copy blindly — each one is answering a specific failure mode you'll hit eventually:

  • retries — reruns a failing test to separate real bugs from flakiness (a test that fails once and passes on retry is flaky, not broken). Keep it at 0 locally so a real bug fails loudly on the first try instead of quietly passing on attempt two while you're not looking.
  • workers — how many tests run in parallel, one browser instance each. CI runners usually have fewer cores than your laptop, so a value tuned locally can starve or overload a shared CI machine — cap it explicitly there rather than trusting Playwright's auto-detection.
  • trace: 'on-first-retry' — only pay the recording cost (CPU, disk, artifact size) when a test is already suspicious, not on every green run. trace: 'on' records everything and is useful for a short debugging session, but bloats CI artifacts fast if left on permanently.
  • projects — the same test file runs once per project, with that project's browser and device settings. A locator that only breaks in WebKit, or a layout that only breaks on a 390px viewport, is exactly the kind of bug a single-browser run would never catch, and the kind that reaches production first.
  • baseURL — lets tests call page.goto('/checkout') instead of hardcoding a host per environment. Combine with an environment variable so the same test file runs unmodified against local, staging, and CI.
03

Debugging tooling

A failing assertion tells you what was wrong. These tools tell you why — by letting you step through, or rewind to, the exact moment it happened. In practice you'll reach for them in roughly this order: codegen while writing a new test, UI mode while a test is actively failing on your machine, and trace viewer once it's failing on someone else's.

Trace viewer

A trace is a scrubbable recording of the whole test run: a DOM snapshot before and after every action, the network log, the console, and a screenshot per step — enough to reconstruct exactly what the browser saw, after the fact, without having to reproduce the failure live.

# record on first retry (set in config, see 02), then open it
npx playwright show-trace trace.zip

This is what earns its keep on a CI-only failure: something failed on a Linux runner you don't have access to, in a state you can't reproduce locally. In CI, upload test-results/ as a build artifact so that trace is one download away instead of "works on my machine" being the end of the investigation.

UI mode

npx playwright test --ui

Runs your suite in a local app with a timeline, a live DOM snapshot per step, locator picking, and a watch mode that reruns automatically on save. This is where most day-to-day debugging should happen — it's the fast, local loop for "why did this test just fail on my machine," before you'd ever reach for trace viewer, which is aimed at failures you can't watch happen live.

Codegen

npx playwright codegen playwrightlab.html

Opens a browser instrumented to record your clicks and typing as Playwright code as you go — useful for a first draft or for figuring out a locator for one stubborn element, less useful as a way to author an entire suite (recorded scripts tend to be brittle and skip the assertions that make a test worth having). Usefully, it also shows the same locator-quality reasoning PlaywrightLab's own inspector does: it prefers roles and test ids over brittle CSS paths, and will visibly hesitate on an element that doesn't have a good one.

Screenshots and video on failure

Already wired up in the via screenshot: 'only-on-failure' and video: 'retain-on-failure'. Cheap to leave on permanently — unlike full tracing, Playwright discards the artifact automatically when a test passes, so the storage cost only shows up on the runs you'd want to inspect anyway. A screenshot answers "what did the page look like," a trace answers "what led up to it" — keep both on and reach for whichever the failure actually calls for.

04

CI

A suite that only runs on your machine isn't a safety net for the team — it's a safety net for you, on the days you remember to run it. The goal here is a green check on every pull request, in a time budget people will actually wait for instead of merging past.

Headless run in GitHub Actions

"Headless" just means no visible browser window — the same Chromium/Firefox/WebKit binaries run identically, just without rendering to a screen, which is the only mode that makes sense on a CI runner. The workflow below is close to the minimum viable setup: install dependencies, install the browsers Playwright needs (a separate step, since they're not npm packages), run the suite, and — critically — upload the report even when the run fails, since if: always() is what saves that artifact from being thrown away with a failed job.

# .github/workflows/playwright.yml
name: Playwright Tests
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 14

Sharding across machines

Split one suite across several parallel jobs — 4 shards at 25 tests each finishes roughly 4x faster than 1 runner working through all 100.

strategy:
  matrix:
    shard: [1, 2, 3, 4]
steps:
  - run: npx playwright test --shard=${{ matrix.shard }}/4

Combine with the workers setting from : shards split test files across machines, workers split them across cores within one machine — you generally want both.

Merging sharded reports

Splitting the suite across 4 shards also splits the report into 4 separate, partial HTML reports — none of which shows the full picture on its own. Each shard job uploads its raw ("blob") results as an artifact; a final job that depends on all of them downloads the artifacts and merges the blobs into the one HTML report you'd actually want to open and click through.

# each shard uploads its blob report, a final job merges them
npx playwright merge-reports --reporter=html ./all-blob-reports
05

API testing

PlaywrightLab's Network panel proves a request happened, but you can't test a JSON API through a browser page. This needs a real HTTP endpoint — the request fixture talks to one directly, no browser involved.

Testing a REST endpoint directly

import { test, expect } from '@playwright/test';

test('GET /users returns a list', async ({ request }) => {
  const res = await request.get('https://jsonplaceholder.typicode.com/users');
  expect(res.ok()).toBeTruthy();
  const users = await res.json();
  expect(users.length).toBeGreaterThan(0);
});

test('GET a missing user returns 404', async ({ request }) => {
  const res = await request.get('https://jsonplaceholder.typicode.com/users/9999');
  expect(res.status()).toBe(404);
});

This is the same pair of endpoints PlaywrightLab's Network panel calls from the browser — hitting them through request instead skips launching a browser, rendering a page, and waiting for the DOM entirely. A UI test that clicks through to check an API response might take 2-3 seconds; the equivalent request call takes milliseconds, which is the difference between a 200-test suite finishing in minutes versus seconds.

Mocking the network instead of calling it

The request fixture above still hits a real backend — fine for testing the API itself, but a UI test that needs to check "what does the page show when this call is slow, empty, or a 500" shouldn't depend on making the real server actually misbehave on demand. page.route() intercepts a request before it leaves the browser and lets you answer with whatever response the test needs, so the UI is exercised against a case that might be rare or impossible to trigger for real.

await page.route('**/api/users', async route => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify([{ id: 1, name: 'Ada' }]),
  });
});

await page.route('**/api/users', route =>
  route.fulfill({ status: 500, body: 'Internal Server Error' })
);

await page.goto('/users');
await expect(page.getByTestId('error-banner')).toBeVisible();

This is also what turns a UI test suite deterministic instead of dependent on a real backend being up, seeded correctly, and fast — three things that are true on a good day and false on the day CI actually needs them. The tradeoff is real: a mocked response can drift from what the API actually returns and the test would never notice, so mock the failure paths and edge cases that are hard to produce for real, and keep at least a few end-to-end tests hitting the genuine API so a real contract break still gets caught.

Seeding state via API, verifying via UI

The pattern that actually earns API testing its keep, and the one most real suites underuse: create data through the API (fast, no flake, no dependency on some other UI flow having worked first), then check the UI reflects it — because the UI is the part users actually see, and no amount of passing API tests proves it renders correctly.

The alternative — driving the UI to create the test data too, e.g. filling out a "new post" form before every test that needs a post to exist — multiplies both runtime and flake risk for setup that isn't what the test is actually about. Reserve full UI-driven setup for the handful of tests whose whole point is that creation flow.

test('a post created via API shows up in the UI', async ({ request, page }) => {
  const created = await request.post('https://jsonplaceholder.typicode.com/posts', {
    data: { title: 'Hello', body: 'World', userId: 1 },
  });
  const { id } = await created.json();

  await page.goto(`/posts/${id}`);
  await expect(page.getByRole('heading')).toHaveText('Hello');
});

Reusing a login for both

Every test that needs to be logged in could log in through the UI first — fill username, fill password, click submit, wait for the redirect. Multiply that by a few hundred tests and logging in becomes a meaningful fraction of total suite runtime, for a step that's identical every single time and isn't what any of those tests are actually checking.

Log in once via request — no browser needed, since it's just an HTTP call — save the resulting session to disk, and every later test — API or UI — starts already authenticated by loading that saved state instead of repeating the login flow. This is the other half of the PlaywrightLab's Auth & session panel sets up: that panel shows what to reuse (a session that survives reload), this is how to create it without a browser in the loop at all.

// global-setup.ts
async function globalSetup() {
  const requestContext = await request.newContext();
  await requestContext.post('/api/login', { data: { user: 'tester', pass: 'playwright' } });
  await requestContext.storageState({ path: 'storageState.json' });
}
Companion to PlaywrightLab — that page teaches locators and interaction patterns on real DOM; this one covers the project-level layer around a suite that no single practice page can demonstrate on its own.
